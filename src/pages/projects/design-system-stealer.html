Design system stealer

Point it at a domain. It reads the live DOM, infers the design system behind it, and generates a shadcn project that replicates it.

By Séverin Marcombes · built on the Claude Agents SDK

Describing a design system in prose is lossy in a way that is easy to underestimate. Ask a model to “make it look like Stripe” and you get a confident pastiche: roughly the right blue, roughly the right radius, and none of the decisions that actually make the thing feel coherent. The facts are all sitting in the DOM. Nobody was reading them.

So this reads them. Point it at a domain and it browses the site, extracts the real computed values rather than its impression of them, and generates a shadcn project that replicates the system as closely as it can.

Facts, not vibes

The first half walks the site with a browser and writes a design system folder from what it observes: the type scale as actually rendered, the spacing rhythm, the colour roles and where each is used, the components that exist and the variants of each, and — the part that separates a good clone from a bad one — how every state differs. Hover, focus, disabled, active. Those are where a design system lives, and they are exactly what prose descriptions drop.

Then it builds

The second half scaffolds a Next.js project with shadcn, installs the component set, and rewrites each component's styling, typography and theme against the extracted facts — using Tailwind's own scale where the target happens to match it, and arbitrary values where it does not. The home page renders a showcase of everything it produced, so the result can be compared against the original side by side.

The prompt is the product

The CLI is thin — it is a Claude Agents SDK loop. The thing that determines whether the output is good is a long, carefully revised PROMPT.md, and the real work was iterating on it: run against a domain, look at what came out, find the instruction that was ambiguous, tighten it, run again.

That loop is why I built it. It is a small, self-contained instance of the argument I keep making: the capability lives in written-down, runnable, improvable software rather than in the model, and it gets better because it is evaluated against something real rather than because anyone described it more eloquently.

What it was tested against

  • → Doctolib — dense product UI, heavy form vocabulary.
  • → Linear — tight type scale, subtle state changes, a system that punishes approximation.
  • → Stripe — the reference point everybody claims to imitate and few actually measure.

Tested against Doctolib, Linear and Stripe.
